# Как работаем вместе

For the current worker check-in cadence and the Agentverse write-area reservation, see [CHECK-IN-PROTOCOL.md](CHECK-IN-PROTOCOL.md). This adds reporting expectations; it does not grant an implementation task.

## Простая схема
Одна папка и разделённые области записи. Координатор — сессия **Viveka.HackatonCoordinator** в ours-codex.

**Никому не выдавать новые задания без прямого указания Тараса.** Подготовленный пакет и вычисленный статус ready не являются разрешением начать. Уже разрешённые задачи и фактические статусы участников отражаются в `docs/status/` и `docs/WORKLOG.md`.

## Режим хакатона: помогать двигаться

В рамках уже разрешённой задачи каждый участник сам делает обратимые подготовительные шаги, проверяет доступные входы и помогает соседям на стыках. Не ждём очередного сообщения Тараса для обычного выбора способа реализации или передачи статуса. Вопросы между агентами отправляем напрямую через Ours и отвечаем при ближайшей проверке почты; если ответ не пришёл, продолжаем независимую часть работы. При блокере сообщаем **одним коротким сообщением**: что именно не работает, что уже проверено, кому и какое действие нужно, что можно делать параллельно. Координатор снимает блокеры и сообщает владельцу только решения, которые действительно требуют его участия.

Это правило не расширяет доступ к приватным данным и не отменяет отказ автоматической проверки: после такого отказа нужна прямо указанная проверкой форма подтверждения. Не выдаём неподтверждённый результат за готовую интеграцию. Исследовательский проход в Muse Code и вызов Meta Model API — разные свидетельства; первый может идти сейчас на разрешённой выборке, второй нужен для воспроизводимого приложения и партнёрского демо, когда настроен ключ.

## Источник состояния
- docs/tasks.json — задачи, зависимости, предлагаемые владельцы, разрешения и свидетельства.
- docs/WORKBOARD.md и reports/STATUS.html — производные представления.
- docs/events.jsonl — append-only журнал изменений статуса.
- docs/status/<identity>.md — собственный отчёт каждого участника; чужой файл не редактировать.
- Ours — доставка сообщений. Принятые решения и результаты сохраняются в файлы; чат не единственная память.

Трекер и общие контракты пишет только координатор. Отчёт исполнителя ещё не done: сначала проверка результата и принятие координатором.

## Старт задачи
1. Тарас разрешил конкретную задачу или явно определённую группу.
2. Координатор записал approval=user и основание разрешения, проверил зависимости и блокеры.
3. Исполнитель ответил ACK с task_id, областью записи, входами и критерием готовности.
4. Координатор перевёл задачу в doing, указал сессию и время.
5. Исполнитель работает только в своей области. Общие интерфейсы менять через запрос координатору.

В общей папке нельзя одновременно редактировать один файл. Если нужен чужой файл — сообщить путь и изменение, дождаться освобождения. Коммиты/слияние общей рабочей копии делает координатор; не использовать git reset/clean/stash для чужих изменений. Отдельные ветки вводить лишь при реальном конфликте и после согласования.

## Передача через Ours
Формат: TASK <id> | ACK / BLOCKED / REVIEW / QUESTION; выполнено; файлы; проверка; неизвестное/риск; что нужно дальше.
В REVIEW указать точный diff/файлы и команды проверки. Координатор отвечает ACCEPTED или REWORK. No response ≠ acceptance.

При блокере сразу сообщить; не переходить на чужую область или платную операцию по собственной инициативе. При потере связи оставить отчёт в своём status-файле. Координатор не выдаёт задачу повторно, пока не выяснил, работает ли прежний исполнитель.

## Проверка
Самопроверка исполнителя — development loop. Независимая оценка проводится отдельно; смена модели сама по себе не обеспечивает независимость. Финальные отложенные случаи не размещать в общей папке, доступной строителю; опубликованный harness и синтетический пример можно хранить здесь. После раскрытия набор становится regression, а не held-out.

## Пересчёт
Из корня проекта:
```sh
python3 reports/build.py
python3 reports/build.py --check
python3 -m unittest discover -s reports/tests
```
Открыть reports/STATUS.html или docs/WORKBOARD.md. Зависимость считается закрытой только при done + свидетельстве. Дашборд показывает техническую готовность, разрешение и занятость отдельно.

Монитор Ours должен жить в отдельной ours-codex сессии. Не утверждать, что он запущен, пока monitor_status это не подтвердил.
